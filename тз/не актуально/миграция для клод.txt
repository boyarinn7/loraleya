**Автор:** дизайнер-архитектор проекта
**Получатель:** шеф-дизайнер (на согласование)
**Статус:** проект заблокирован на этапе запуска вариативных товаров

## 1. Суть проблемы

### 1.1. Что должно работать

В магазине LoraLeya каждое изделие (дорожка, скатерть, набор) выпускается в **17 цветах ткани**. Покупатель на странице товара должен видеть селектор цвета, выбирать «Бирюза» или «Бронза», получать актуальную цену и кнопку «Купить» — стандартное поведение вариативного товара в WooCommerce.

Технически это реализуется через механизм **атрибутов товара** — таксономию, термины которой WooCommerce подставляет в выпадающий список вариаций.

### 1.2. Что происходит сейчас

Создано 5 пилотных товаров для цвета «Бирюза»: дорожка (4 размера), скатерть (3 размера), салфетка, куверт, готовый набор (4 комплектации). Из них **3 вариативных товара не работают:**

- В админке у каждой вариации в графе «Цвет ткани» стоит «**с любым значением**» вместо конкретно «Бирюза»
- Статус товаров — «**Нет в наличии**»
- Цена показывается **диапазоном** `1 — 590 ₽` вместо нормальной цены вариации
- На фронте товары **нельзя добавить в корзину**

Простые товары (салфетка и куверт) работают, потому что у них нет вариаций — там цвет хранится как обычная привязка к таксономии.

### 1.3. Почему так получилось — технический корень

Когда проект начинался, для хранения цветов завели **кастомную таксономию** `fabric_color` — обычную WordPress-таксономию, не связанную с WooCommerce. На ней построено:

- 17 цветов с метаданными `color_hex` (для отрисовки цветовых кружков в палитре)
- Страницы цветов по адресу `/color/{slug}/` (например, `/color/biryuza/`) — на них уже есть внешние ссылки, ломать нельзя
- Шаблон страницы цвета `taxonomy-fabric_color.php`
- Блоки палитры на главной и на страницах сценариев

**Когда подключили WooCommerce и попробовали использовать `fabric_color` как атрибут товара** — выяснилось, что WooCommerce работает **только с атрибутами, имя которых начинается с префикса `pa_`** (от англ. *product attribute*). Это его архитектурное требование, зашитое в десятки внутренних функций. Без этого префикса WC не понимает, что таксономия — это атрибут, и не подгружает её термины в селектор вариаций. Отсюда «с любым значением».

### 1.4. Что уже пробовали и почему не сработало

Прежде чем выйти на текущий план, перебрали три обходных пути:

**Попытка 1.** Зарегистрировать `fabric_color` в реестре WC-атрибутов через фильтр `woocommerce_attribute_taxonomies`. WC проглотил регистрацию, но **дополнительно создал пустую таксономию `pa_fabric_color`** — то есть в системе появилось два параллельных хранилища. Откатили.

**Попытка 2.** Принудительно привязывать вариации к терминам `fabric_color` через программный вызов `wp_set_object_terms()`. Код отрабатывает без ошибок, в БД привязки создаются — **но WC их игнорирует** при отрисовке селектора, потому что не считает `fabric_color` атрибутом.

**Попытка 3.** Зарегистрировать `fabric_color` как атрибут WC, но через комбинацию из трёх фильтров (`woocommerce_attribute_taxonomies` + `woocommerce_attribute_taxonomy_slug` + `woocommerce_taxonomy_args_fabric_color`) принудительно запретить WC добавлять префикс `pa_`. Заказчик выполнил все шаги: залил код, очистил транзиенты WC, пересохранил товар — **поведение не изменилось**, в админке всё та же «с любым значением».

**Вывод после трёх попыток:** требование префикса `pa_` зашито в WC слишком глубоко, обходными путями его не убрать. Дальнейшие попытки «договориться» с WC — это потеря времени.

## 2. Предлагаемое решение

### 2.1. Концепция

**Перевести таксономию `fabric_color` на стандартный для WC формат `pa_fabric_color`** — то есть не бороться с WooCommerce, а лечь в его архитектуру.

При правильном выполнении это:
- Чисто решает проблему вариаций — WC автоматически видит атрибут
- Сохраняет все 17 цветов с их метаданными
- Сохраняет URL `/color/{slug}/` в неизменном виде
- Сохраняет привязки уже созданных товаров
- Не ломает фронтенд — палитра, страницы цветов, конструктор

### 2.2. Почему это безопасно — технический разбор

В WordPress таксономия и её термины хранятся в трёх таблицах:

- `wp_terms` — сами термины («Бирюза», «Бронза» и т. д.) с `term_id`
- `wp_term_taxonomy` — поле `taxonomy` указывает, к какой таксономии принадлежит термин (`fabric_color` → меняем на `pa_fabric_color`)
- `wp_term_relationships` — связи терминов с товарами через `term_taxonomy_id`

Ключевой факт: **миграция меняет только одно поле в одной таблице** (`taxonomy` в `wp_term_taxonomy`). Все ID — `term_id`, `term_taxonomy_id` — остаются прежними. Поэтому:

- Метаданные цветов (`color_hex`) не трогаются — они хранятся в `wp_termmeta` по `term_id`
- Привязки товаров к цветам не трогаются — они в `wp_term_relationships` по `term_taxonomy_id`
- Внешние ссылки на `/color/biryuza/` продолжают работать — их сохранит rewrite-правило

Это хирургическая операция, а не пересборка БД.

### 2.3. План работ — 5 этапов

**Этап 0. Страховка (заказчик).**
Свежий бэкап UpdraftPlus с включённой БД. Установка двух плагинов для SQL-доступа: **Better Search Replace** (для корректного обновления сериализованных данных в `wp_postmeta`) и **WP Query Console** (для прямого UPDATE по таблице `wp_term_taxonomy`). Без этого этапа никаких работ не начинается.

**Этап 1. Код — регистрация атрибута (агент, отдельный коммит).**
В `functions.php` зарегистрировать `pa_fabric_color` как атрибут WC через фильтр `woocommerce_attribute_taxonomies`. Дополнительно через фильтр `woocommerce_taxonomy_args_pa_fabric_color` переопределить `rewrite => ['slug' => 'color']` — это сохраняет URL-структуру `/color/{slug}/` неизменной. Старая регистрация `fabric_color` удаляется. Коммит изолированный, легко откатывается.

**Этап 2. Код — обновление шаблонов и хелперов (агент, отдельный коммит).**
Глобальный поиск-замена `'fabric_color'` → `'pa_fabric_color'` по проекту. Затронутые файлы: `taxonomy-fabric_color.php` (переименовать в `taxonomy-pa_fabric_color.php`), `front-page.php`, `single-scenario.php`, импортер `tools/import-products.php`, JS-файлы. Все хуки админки для редактирования цвета (`fabric_color_add_form_fields` и пр.) переключаются на новые имена.

**Этап 3. SQL-миграция (заказчик, после заливки кода).**
Через WP Query Console выполнить один запрос:
```sql
UPDATE wp_term_taxonomy SET taxonomy = 'pa_fabric_color' WHERE taxonomy = 'fabric_color';
```
Через Better Search Replace — пройтись по `wp_postmeta` с заменой `fabric_color` → `pa_fabric_color` (это нужно для поля `_product_attributes`, которое хранится сериализованным массивом — обычный SQL сломал бы сериализацию, а Better Search Replace пересчитывает длины строк корректно).

**Этап 4. Финализация (заказчик).**
Сохранить «Постоянные ссылки» в админке (для flush rewrite rules). Очистить кэш WP Super Cache. Открыть каждый из 5 товаров и нажать «Обновить» для ресинхронизации атрибутов.

**Этап 5. Проверка.**
Селектор вариации показывает «Бирюза» вместо «с любым значением». Товары в статусе «В наличии». Цены — конкретные, не диапазоном. Страница `/color/biryuza/` открывается. Палитра на главной отрисована цветными кружками. Импортер при следующем запуске работает с `pa_fabric_color`.

### 2.4. Точки отката на каждом этапе

| Что сломалось | Как откатываем |
|---|---|
| Код после этапа 1 или 2 | `git checkout main`, удалить ветку |
| БД после этапа 3 | UpdraftPlus → восстановить только БД из свежего бэкапа |
| Альтернативный откат БД | Обратный SQL: `UPDATE wp_term_taxonomy SET taxonomy = 'fabric_color' WHERE taxonomy = 'pa_fabric_color'` |
| Поломались URL цветов | Пересохранить «Постоянные ссылки» |

Все этапы изолированы. Откат на любом из них возвращает систему в текущее (нерабочее, но стабильное) состояние без потери данных.

### 2.5. Что критично сохранить

17 терминов цветов с их метаданными `color_hex` (без них палитра становится серой, сайт визуально умирает), URL `/color/{slug}/` (на них могут быть внешние ссылки), привязки 5 уже созданных товаров к цвету «Бирюза».

## 3. Оценка трудозатрат и рисков

**Время выполнения:** 2–3 часа активной работы при условии что бэкап и плагины готовы. Из них код агента — около часа, SQL-миграция и проверка — час.

**Главный риск:** сериализованные данные в `_product_attributes`. Если использовать обычный SQL вместо Better Search Replace — сломается сериализация массива атрибутов и товары откроются с ошибкой. Митигация — обязательное использование Better Search Replace для этой таблицы.

**Второй риск:** rewrite-правила. Если не сохранить «Постоянные ссылки» после миграции — `/color/biryuza/` отдаст 404. Митигация — это последний обязательный шаг чек-листа.

**Третий риск:** кэш WP Super Cache может показывать старые 404 после миграции. Митигация — принудительная очистка кэша в чек-листе.

**Что НЕ является риском:** потеря товаров, потеря медиатеки, потеря настроек темы. Эти данные миграция не трогает.

## 4. Что разблокируется после миграции

Завершённый этап миграции открывает дорогу к финальной сборке магазина:

**MVP (1–2 дня):** связка кнопок `+`/`−` с WC-корзиной через готовые AJAX-хуки, дышащая иконка корзины с модалкой, удаление старой плавающей полоски с суммой.

**Деньги (2–3 дня):** настройка ЮKassa (требует юрданные от kurenkova), юридические страницы (Доставка, Возврат, Оферта, Политика конфиденциальности), тестовый боевой заказ.

**Косметика (1–2 дня):** стилизация дефолтных страниц WC под тёмную тему LoraLeya, расширение каталога на бежевый и бронзу.

Без миграции вся эта работа упирается в неработающие вариативные товары и теряет смысл.
