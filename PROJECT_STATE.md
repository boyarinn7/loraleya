## Обычный заказ WooCommerce

- Checkout создаёт неоплаченный заказ для согласования.

- `customer_processing_order` означает: заказ принят LoraLeya в работу.
- `customer_completed_order` означает: заказ физически передан службе доставки и находится в пути.

## Индивидуальные заказы

### Клиентская форма

Старая модель, привязанная к форме стола и количеству персон, заменена позиционной моделью `items_v2`.

- По умолчанию создаётся одна позиция; число изделий не ограничено.
- Каждая позиция содержит изделие, размер / параметры, цвет, количество и комментарий к изделию.
- Поддерживаются скатерти, дорожки, салфетки, куверты, шторы и `Другое`.
- Поле «Название изделия» появляется только для `Другое` и не участвует в validation, когда скрыто.
- Палитра использует все 17 реальных цветов `pa_fabric_color`; desktop-сетка — `9 + 8`.
- Свотчи, подписи и отступы увеличены; адаптивность и внешний вид вручную проверены на staging.
- `+ Добавить ещё изделие` оформлено отдельной вторичной плашкой.
- Из новой клиентской модели удалены форма и размеры стола, количество персон и дополнительные опции.
- Hero: «Создадим текстиль специально для вас».

Первоначальная заявка сразу собирает ФИО, телефон, email и адрес доставки. Отдельные обязательные поля города, ПВЗ, курьера и перевозчика в клиентскую форму не добавляются. Способ получения и детали доставки менеджер уточняет при согласовании.

Финальная нижняя последовательность формы:

1. `Ваша заявка`.
2. `Комментарий к заказу`.
3. Согласие на обработку персональных данных.
4. Пояснение о предварительном согласовании.
5. `Отправить заявку`.

Общий комментарий ко всей заявке существует только один. Комментарии отдельных изделий остаются внутри соответствующих позиций.

### Хранение и WooCommerce

- Новые заявки используют структурированную модель `items_v2`.
- После согласования каждое изделие создаётся отдельным Woo line item с собственными размером, цветом, quantity, unit price и line total.
- Разные цвет или размер всегда означают отдельную позицию.
- Общий total равен сумме товарных строк; доставка в первоначальный Woo total не входит.
- Custom Woo items сохраняют `product_id = 0`; технический публичный товар не создаётся.
- Legacy-заявки и legacy-заказы продолжают работать по старому пути.
- Сохраняются immutable original snapshot, duplicate/idempotency protection, locks, reconciliation/converted recovery, partial-failure cleanup, HPOS-safe Woo CRUD и guest/existing customer logic.
- Theme-level Fivepost guard для `product_id = 0` сохраняется.

После создания Woo order становится основной рабочей карточкой, а ИЗ-заявка — исторической/read-only. Payment workflow: `on-hold → pending → customer_invoice → order-pay`. Standard admin `WC_Email_New_Order` для individual Woo orders отключён; обычные Woo orders не затронуты.

### YooKassa: первый платёж и первый чек

Для individual order №946 боевой платёж `100 ₽` успешно принят, первый чек создан и фискализирован. В чек корректно переданы `Куверты / 24×9 / Голубой`, quantity `1`, сумма `100 ₽`, признак «без НДС» и email покупателя. Individual line item с `product_id = 0` корректно проходит в первый чек.

На staging заказ автоматически не сменил статус после оплаты. Подтверждённая причина: боевой YooKassa callback настроен на `https://loraleya.ru/?yookassa=callback`, а staging расположен на `/test/`. Боевой callback ради staging-тестов не менять. Автоматическую обработку `payment.succeeded` проверить при production rollout / production-safe тесте.

### Маркировка / КИЗ

Контрольный обычный staging-товар сначала показывал «Маркировка: Не требуется», потому что в его карточке отсутствовали штатные настройки. После восстановления категории «Товары легкой промышленности», единицы «Штука, единица товара» и количества в упаковке `1` у обычного заказа появился штатный `+`.

YooKassa 2.16.3 прекращала обработку individual line item из-за отсутствующего `WC_Product` при `product_id = 0`. Vendor YooKassa не изменялся. Интеграционный слой добавлен в `inc/yookassa-individual-marking.php` и подключён из `functions.php`.

- Для `tablecloth`, `runner`, `napkins`, `kuverts`, `curtains` используются штатные параметры маркировки товаров лёгкой промышленности.
- `other` автоматически маркируемым не считается.
- Woo №946 в статусе `Обработка`: штатный `+` появился, КИЗ введён и сохранён штатным механизмом YooKassa, отображается зелёный индикатор — PASS.
- В многопозиционном Woo №949 marking action отображается у обеих individual-позиций — PASS.

Отложен финальный тест `КИЗ → Выполнен → второй чек → фактический вывод КИЗ из оборота`: по тестовому платежу №946 был запрошен возврат, поэтому реальный КИЗ специально не выводился из оборота. Тест выполнить после перехода staging-версии в боевую среду; при необходимости внести отдельный точечный patch.

Известный не блокирующий нюанс: у individual items `+` может отображаться раньше статуса `Обработка`. Сейчас не исправлять; вернуться только при необходимости после production regression.

## Индивидуальный заказ — правило оплаты

Утверждённое правило:

- после согласования всех параметров, срока изготовления и стоимости изделия покупатель оплачивает 100% стоимости изделия до начала изготовления;
- стоимость доставки в стоимость изделия не входит;
- 5Post: Москва и Московская область — бесплатно, другие регионы — 250 ₽; эти 250 ₽ не входят в первоначальную оплату 100% стоимости изделия и оплачиваются покупателем отдельно до передачи заказа в 5Post; способ доступен только при соответствии фактических габаритов и веса готового изделия требованиям доставки через постамат;
- если после изготовления заказ не соответствует требованиям 5Post по габаритам или весу, покупателю предлагается другой доступный способ доставки;
- СДЭК и Яндекс: покупатель оплачивает стоимость доставки при получении по тарифам выбранной службы доставки;
- передача или доставка готового заказа от LoraLeya до выбранной службы доставки осуществляется за счёт LoraLeya.

Отдельная архитектура двух платежей за изделие больше не нужна. Initial Woo order и payment request работают с одним платежом в размере 100% стоимости изделия. Первый боевой платёж и первый чек для individual line item проверены; автоматический callback staging и финальный второй чек с выводом КИЗ остаются отдельными production-safe проверками.

## Правила экономии лимита Codex

1. Codex не запускается без конкретной задачи. Сначала задача определяется в ChatGPT, затем формируется точное задание Codex.
2. Одна логическая задача — один запуск Codex. Не смешивать в одном запуске независимые блоки: письма, оплату, доставку, маркировку и т. п.
3. Аудит/чтение выполнять только если архитектура неясна. После аудита — минимальный patch. Не исследовать повторно уже подтверждённую архитектуру без новой причины.
4. Для восстановления контекста использовать `PROJECT_STATE.md`, `docs/DECISIONS.md` и daily-файлы вместо повторного пересказа всей истории проекта.
5. Уровень интеллекта Codex:
   - **Средний** — обычные локальные изменения, тексты, документация, простые проверки;
   - **Высокий** — WooCommerce workflow, платежи, статусы, HPOS, idempotency и другие критичные runtime-механизмы;
   - **Очень высокий** — только действительно сложные архитектурные или особо рискованные задачи.
6. Перед каждым заданием Codex уровень интеллекта указывается пользователю по-русски.
7. Задание Codex формируется одним цельным копируемым блоком.
8. Не поручать Codex проверки, которые быстрее и надёжнее выполнить вручную на staging: внешний вид письма, FAQ, оферта, отображение полей и похожие визуальные проверки.
9. После patch порядок работы: `diff → загрузить только необходимые файлы на /test/ → проверить`.
10. Если тест уже подтвердил механизм, не повторять его без причины.
11. Если проверяемая логика не зависит от конкретной службы доставки, не повторять одинаковый тест для 5Post, СДЭК и Яндекс только «для уверенности».
12. Не делать массовые рефакторинги ради красоты. Предпочитать минимальный безопасный patch и переиспользование уже проверенного кода.
13. Не делать отдельный commit/checkpoint после каждой мелкой правки. Commit создаётся после законченного логического блока.
14. Новый чат Codex открывается для нового крупного этапа, а не для каждой мелкой задачи. Предыдущие чаты сохраняются как архив.
15. После результата Codex сначала анализировать результат в основном ChatGPT-чате и только затем решать, нужен ли следующий запуск.
16. Не просить Codex повторно «перепроверить всё подряд», если diff и нужные тесты уже прошли.
17. Ответ Codex должен быть настолько кратким, насколько позволяет задача: результат, diff, проверки, blocker. Не требовать длинных отчётов без необходимости.
18. Manual approvals сохраняются включёнными. Безопасность важнее небольшой экономии лимита.

Сначала думаем в основном ChatGPT-чате → при необходимости один аудит → один минимальный patch → проверяем diff → загружаем только нужные файлы на /test/ → ручные проверки выполняем сами, когда это дешевле → commit после завершённого логического блока.
