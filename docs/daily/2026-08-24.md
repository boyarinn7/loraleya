## Переоценка production rollout strategy

После checkpoint `6d78431f5978273ec750d5c228372f977e1c450d` стратегия переноса пересмотрена.

- На текущем production отсутствуют реальные заказы.
- Решено не выполнять параллельные ручные правки production и не делать сложный merge двух рабочих БД.
- `/test/` становится источником истины и финальной версией для полного одноразового переноса в корень домена.
- Сформирован checklist из четырёх фаз: Finish staging, Freeze, One-time migration, Production acceptance.
- До переноса обязательны SEO protection, проверка Метрики, legal/business texts, privacy, emails, marking quantity > 1, mobile и normal-order regression, сверка environment, credentials и test-data cleanup.
- Перед миграцией выполняются final regression, checkpoint и полный backup production.
- Перенос включает files, plugins, uploads и database; URL replacement выполняется serialized-safe способом.
- После миграции проводится controlled real order для проверки callback, чеков, КИЗ, second receipt, вывода из оборота и Метрики.
- Главный SEO-приоритет: не допустить индексацию `/test/` и одновременно не перенести staging `noindex` на новый production.
- После успешного rollout `/test/` не должен оставаться публичной индексируемой копией.
- Финальный second receipt / КИЗ exit является production acceptance test, а не staging blocker.
- Partial refund маркированного заказа остаётся отдельной задачей и не считается blocker при запрете использовать непроверенный automatic partial refund как подтверждённый workflow.
